# Методика эксперимента

## Цель и гипотеза

Эксперимент проверяет, насколько план теста, построенный системой по
трассировкам реального использования, воспроизводит исходную нагрузку —
и сравнивает его с планом, составленным вручную по документации API.

Гипотеза: расхождение профиля, полученного прогоном автоматически
построенного плана, с эталонным профилем меньше, чем расхождение профиля
от ручного плана. Расхождение измеряется по трём показателям: состав
операций в долях, интенсивность прихода сессий, статистики пауз
(медиана и 90-й перцентиль).

## Прогоны

Прогон A (эталон). Генератор активности работает на стенде по эталонному
профилю, зашитому в его код: три сценария с весами 30/30/40 и паузами,
равномерно распределёнными на отрезке 1–3 с. Параметры генератора
(интенсивность, длительность, зерно) фиксированы и записываются в журнал
прогона.

Прогон B (автоматический план). Система строит профиль по трассировкам
прогона A (команда build-profile), генерирует план теста (generate)
и выполняет его в JMeter в режиме без графического интерфейса.

Прогон C (ручной план). План составляется человеком по документации API
стенда (demo-stand/README.md) без доступа к эталонному профилю: тот же
набор операций, а доли, паузы и интенсивность выбираются на усмотрение
составителя. План выполняется так же, как B.

## Эталонный профиль

Эталон не измеряется, а вычисляется из параметров генератора, поэтому
известен точно. Среднее число операций на сессию:
0.3·1 + 0.3·2 + 0.4·6 = 3.3. Отсюда доли операций:

| Операция | Доля |
| --- | --- |
| GET /api/products | 1.0 / 3.3 = 30.30 % |
| GET /api/products/{id} | 0.7 / 3.3 = 21.21 % |
| POST /api/orders | 0.4 / 3.3 = 12.12 % |
| POST /api/orders/{uuid}/items | 0.4 / 3.3 = 12.12 % |
| POST /api/orders/{uuid}/checkout | 0.4 / 3.3 = 12.12 % |
| GET /api/orders/{uuid} | 0.4 / 3.3 = 12.12 % |

Паузы равномерны на [1000, 3000] мс: медиана 2000 мс, 90-й перцентиль
2800 мс. Интенсивность равна параметру запуска генератора.

## Порядок измерений

Профили прогонов B и C измеряются одной линзой: трассировки прогона
выгружаются из Jaeger за окно прогона, пропускаются через тот же конвейер
профилировщика (команда build-profile), и полученный профиль сравнивается
с эталонным командой compare. Никакие характеристики планов не берутся
из самих планов — только поведение на стенде, как оно видно трассировке.

Последовательность одного измерения:

1. Стенд поднимается заново (compose up), состояние сервисов чистое.
2. Выполняется прогон (A — генератором, B и C — JMeter по плану).
3. После окончания выдерживается пауза в 30 с на доотправку спанов.
4. Профиль строится по трассировкам окна прогона и сохраняется в базу.
5. Раз с эталоном считается командой compare.

## Условия воспроизводимости

Генератор запускается с фиксированным зерном; каталог товаров зашит
в код стенда и одинаков при каждом старте. Между прогонами стенд
перезапускается целиком, чтобы заказы из прошлого прогона не влияли
на следующий. JMeter работает в режиме без графического интерфейса,
длительность всех прогонов одна и та же. Ресурсные атрибуты среды
(имя хоста, идентификаторы контейнеров, версии ОС и процесса) из
выгрузок удаляются: к нагрузке они отношения не имеют.
